# v6.1 Plan: Restore Harmonic Loss

## Context

`AGENTS.md` is newer than `CLAUDE.md` and matches the architecture described in the prompt, so this plan treats it as the current project guide. The conditioning ablation from `experiments/2026-05-18-conditioning-ablation.md` shows that `checkpoints/v6_best.pt` does not meaningfully use `chord_ids`, `phrase_id`, or `artist_id`; `chord_shuffled` is effectively tied with baseline pitch CE. The likely regression is that `src/training/train_v6.py` dropped the v5b harmonic auxiliary loss from `src/training/train_v5b.py`.

This plan now uses a two-stage experiment. The first run is a literal v5b loss port so the causal question is clean. The second run is the musically corrected version, only if the literal port fails or only partially succeeds.

## Experiment Design

### v6.1.0: literal v5b port

This is the right first experiment. It changes the fewest variables: restore the harmonic loss code path with `STRONG_BEAT_POS = {0, 4, 8, 12}`, use `pos_in_phrase`, use `chord_ids[:, 0]`, keep `LABEL_SMOOTHING = 0.0`, do not add dataset fields, do not rebuild the cache, and finetune from `checkpoints/v6_best.pt`. This tests the pure regression hypothesis: "the v5 to v6 commit caused conditioning collapse by dropping this specific auxiliary loss."

### v6.1.1: musically correct harmonic loss

Run only if v6.1.0 is no-effect or partial-success. This version adds `target_is_strong_beat` from WJazzD `beat in {1, 3}` and `target_chord_id` from forward-filled chord symbols, stored in a new cache file at `data/processed/notes_v6_1_cache.pt`. This tests the stronger engineering hypothesis: "the harmonic auxiliary works better when anchored to the note's actual beat and active chord."

### Why not combine them first?

The combined approach would probably be a better final implementation if it succeeds, but it would conflate two effects: restoring the missing loss and correcting the loss anchors. Since the ablation finding specifically implicates code dropped during the v5b to v6 training-script rewrite, experimental cleanliness is worth preserving. v6.1.0 should be the first authorized implementation.

## 1. Strong-Beat Semantics

### Answer / recommendation

v6's `pos_in_phrase` has the same field name and range as v5b's training code expected, but it does not literally mean "downbeat." In `src/data/note_dataset.py:147-148` and `:163-168`, it is the ordinal note index within the phrase, capped at 15. The cache confirms values `0..15`, with position 15 absorbing all later notes. Raw phrase examples show that positions `{0, 4, 8, 12}` land on many WJazzD `beat` values, not consistently on beat 1. For v6.1.0, keep the v5b constants anyway because the point is literal regression testing. For v6.1.1, replace the proxy with `target_is_strong_beat = beat in {1, 3}`.

### Exact code change required

v6.1.0 only modifies `src/training/train_v6.py`; no dataset or cache changes:

```python
HARMONIC_WEIGHT = 0.15
STRONG_BEAT_POS = frozenset({0, 4, 8, 12})
```

Port the v5b `harmonic_penalty` strong-position mask from `src/training/train_v5b.py:81-106` as-is:

```python
strong = torch.zeros(pos_in_phrase.size(0), dtype=torch.bool, device=pos_in_phrase.device)
for p in STRONG_BEAT_POS:
    strong |= (pos_in_phrase == p)
```

v6.1.1, if needed, modifies `src/data/note_dataset.py` around `:137-149` so each note encoding carries a beat-derived flag:

```python
beat = int(note.get("beat", 0) or 0)
is_strong_beat = beat in {1, 3}
note_enc.append((note["pitch"], dur_tok, is_rest, min(i, MAX_POS_IN_PHRASE), is_strong_beat))
```

Then propagate `target_is_strong_beat` through sample creation, `__getitem__`, and `collate_note_window`.

### Edge cases / risks

The v6.1.0 strong-beat name is historically inherited but musically imprecise. Label it in config/logs as `strong_beat_source="pos_in_phrase_literal_v5b"` to avoid future confusion. In v6.1.1, WJazzD beat values outside 1-4 should be treated as non-strong unless the dataset later adds meter-aware logic.

## 2. Chord Token Indexing

### Answer / recommendation

For v6.1.0, use v5b's `chord_ids[:, 0]` indexing exactly. It is not musically reliable in v6: `chord_ids` is a variable-length list of phrase chord-change tokens, `chord_mask` only distinguishes padding, and the first chord can be the empty-string chord token. But that imperfection is part of the literal v5b port and is necessary for the clean regression test. For v6.1.1, add `target_chord_id` because neither `chord_ids[:, 0]` nor `chord_mask` can identify the chord under the target note.

### Exact code change required

v6.1.0 ports this v5b line into `src/training/train_v6.py`:

```python
c_ids = chord_ids[strong, 0]
```

The `harmonic_penalty` signature for v6.1.0 remains:

```python
def harmonic_penalty(pitch_logits, pos_in_phrase, chord_ids, chord_tone_tensor):
```

v6.1.1 modifies `src/data/note_dataset.py` while building each transposed flat sequence. Keep `chord_ids_t` as the encoder context, but add a per-target active chord:

```python
current_chord = None
for phrase_int, notes, note_enc, tempo in phrase_data:
    trans_ids = _transposed_chord_changes(notes, chord_tok, semitones)
    ...
    for note, encoded in zip(notes, note_enc):
        if note.get("chord"):
            current_chord = note["chord"]
        effective_chord = current_chord or "NC"
        target_chord_id = torch.tensor(
            chord_tok.encode(transpose_chord_symbol(effective_chord, semitones)),
            dtype=torch.long,
        )
```

Then update sample creation, cache loading, and collation:

```python
"target_chord_id": target_chord_id,
```

v6.1.1 harmonic loss signature becomes:

```python
def harmonic_penalty(pitch_logits, target_chord_id, target_is_strong_beat, chord_tone_tensor):
```

with:

```python
strong = target_is_strong_beat.bool()
valid_chord = chord_tone_tensor[target_chord_id].sum(dim=-1) > 0
mask = strong & valid_chord
c_ids = target_chord_id[mask]
```

### Edge cases / risks

v6.1.0 may fail because the literal anchor is noisy; that would not disprove the value of harmonic loss, only the literal-port hypothesis. v6.1.1 must forward-fill chord symbols across phrase boundaries because raw WJazzD notes often use `""` for continuation. Do not infer target chord from `chord_mask`; it has no note-to-chord alignment information.

## 3. Label Smoothing

### Answer / recommendation

Keep `LABEL_SMOOTHING = 0.0` for v6.1.0 and v6.1.1 first attempts. Restoring label smoothing at the same time as harmonic loss would change another training variable. The tradeoff is that v5b used `label_smoothing=0.1`, so if harmonic restoration is promising but underpowered, run a follow-up with `LABEL_SMOOTHING = 0.1` after the harmonic-loss result is understood.

### Exact code change required

No value change in `src/training/train_v6.py:27`:

```python
LABEL_SMOOTHING = 0.0
```

Add the effective value to `wandb.init(... config=...)`. For v6.1.0 also log:

```python
harmonic_weight=HARMONIC_WEIGHT,
strong_beat_source="pos_in_phrase_literal_v5b",
target_chord_source="chord_ids_col0_literal_v5b",
```

For v6.1.1, change those config strings to:

```python
strong_beat_source="wjazzd_beat_in_{1,3}",
target_chord_source="forward_filled_target_chord_id",
```

### Edge cases / risks

The acceptance ablation should always compute reported CE with unsmoothed `nn.CrossEntropyLoss(label_smoothing=0.0)`, regardless of training setting, so deltas remain comparable with the 2026-05-18 table.

## 4. Finetune vs Retrain

### Answer / recommendation

Finetune first from `checkpoints/v6_best.pt` for 5-10 epochs with a fresh optimizer and lower LR. Use LR `1e-4`, lower than v6's original `5e-4`, and reset optimizer/scheduler state because the objective has changed and the checkpoint's scheduler position is tied to the old loss. Loading old optimizer moments would bias the first harmonic updates toward the previous no-harmonic trajectory. Run 8 epochs as the default middle ground, with early stopping still active. Save new checkpoints so `v6_best.pt` remains the baseline.

## Cache Validation Test for v6.1.1

### Recommendation

Add a unit test before any v6.1.1 training that validates the new cache fields against manually computed expectations on a small known sample. This is necessary because a silent forward-fill or transposition bug would corrupt every harmonic target and might only show up later as a failed ablation.

### Exact code change required

Create `tests/test_v6_1_cache_fields.py`. The test should avoid rebuilding the full cache. It should load exactly three phrases from `data/processed/phrases_all_with_tempo.json`, build samples through the same dataset/cache helper path on those phrases, and compare expected fields.

Implementation shape:

```python
def _expected_targets(phrases, chord_tok, semitones):
    current_chord = None
    expected = []
    for ph in phrases:
        for note in sorted(ph["notes"], key=lambda n: n["onset"]):
            if note.get("chord"):
                current_chord = note["chord"]
            effective = current_chord or "NC"
            target_chord_id = chord_tok.encode(transpose_chord_symbol(effective, semitones))
            target_is_strong = int(note.get("beat", 0) or 0) in {1, 3}
            expected.append((target_chord_id, target_is_strong))
    return expected
```

The production implementation should expose a small helper such as:

```python
def build_samples_from_phrases(phrases, chord_tok, note_tok, artist_tok, phrase_tok, semitones_list):
```

or a narrower helper for effective chord/beat target computation. The test then selects three stable phrases, for example the first three non-empty phrases from one solo, runs the helper with `semitones_list=[0, 2]`, and asserts:

```python
assert sample["target_chord_id"].item() == expected_chord_id
assert sample["target_is_strong_beat"].item() == expected_is_strong
```

Also include at least one note where `note["chord"] == ""` to prove forward-fill behavior, and at least one transposed case to prove `transpose_chord_symbol()` is applied before tokenization.

### Edge cases / risks

Avoid a test that only checks shapes or field existence; that would miss the dangerous bugs. Also avoid depending on global full-cache sample indexes because changing phrase filtering or transposition order would make the test brittle. Test a small controlled phrase slice through the same helper used by the cache builder.

## Final Success Gate

The v6.1 fix is accepted only if the ablation artifact reports:

```text
chord_shuffled Δ pitch CE >= +0.10 vs baseline
```

on the same `SEED=42` 100,000-window validation subset. Partial success is `+0.05` to `+0.10`; below `+0.05` means that stage did not sufficiently repair conditioning use. If v6.1.0 reaches strong success, stop there and preserve the clean causal conclusion. If not, proceed to v6.1.1.
